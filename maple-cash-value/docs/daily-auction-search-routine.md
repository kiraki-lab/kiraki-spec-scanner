# 매일 경매장 검색 루틴 지시서

이 문서는 메이플 캐시샵 계산기의 경매장 가격 데이터를 매일 갱신하기 위한 작업 지시서다. 목표는 하루 검색 제한 100회 안에서 계산에 가장 중요한 항목부터 확인하고, 확인 결과를 `data/auction-prices.json`에 일관된 형식으로 반영하는 것이다.

## 목표

- 캐시샵에서 직접 살 수 있는 상품과 직업 패키지 구성품의 경매장 최저가를 확인한다.
- 검색 제한 100회 안에서 결론에 필요한 항목을 우선 처리한다.
- 후보 없음, 매물 없음, 미확인을 구분해서 계산기 상태가 투명하게 보이도록 한다.
- 뽑기 결과물처럼 캐시샵에서 직접 살 수 없는 항목은 기본 검색 대상에서 제외한다.

## 핵심 원칙

1. 패키지는 패키지명 자체가 아니라 구성품명으로 검색한다.
2. 검색 전에는 반드시 기존 검색어를 지운다.
3. URL의 keyword 검색 결과만 믿지 않는다. 자동완성 후보를 선택한 뒤 `필터 검색`을 눌러 확인한다.
4. 후보가 안 뜨면 그 자리에서 `no_candidate`로 기록하고 추가 검색을 낭비하지 않는다.
5. 후보는 뜨지만 결과가 0건이면 `no_listing`으로 기록한다.
6. 가격은 첫 결과 행의 `메소` 바로 앞 줄을 사용한다. 전투력증가량 숫자를 가격으로 읽지 않는다.
7. 괄호 앞 공백 차이는 alias로 처리한다. 예: 데이터 `슈트(여)`, 경매장 후보 `슈트 (여)`.
8. 검색 제한 경고가 뜨면 즉시 중단하고, 남은 항목은 다음 날 `unverified`로 넘긴다.

## 검색하지 않는 항목

- 뽑기 결과물: 예) `쁘띠 주황버섯의 간식` 같은 원더베리/루나 결과물
- 경매장 판매 불가 상품: 예) 스페셜 프라이스팩, 패스류
- 사용자가 의미 없는 품목이라고 확정한 수동체크 항목
- 캐시샵 직접 구매 상품인지 불명확한 펫/간식/확률형 결과물

확률형 상품은 상품 자체만 검색한다. 예: `위습의 원더베리`, `루나 크리스탈`, `스페셜 루나 크리스탈`.

## 하루 검색 예산

하루 제한 100회를 다음처럼 쓴다.

- 10회: 전날 미확인/파싱 실패/검색 제한 직전 항목 재확인
- 70회: 신규 핵심 구성품 검색
- 10회: 후보명 불일치 항목 확인
- 10회: 여유분 및 오류 재검색

80회 정도를 넘기면 남은 항목 수를 보고 계속할지 판단한다. 95회 이후에는 신규 큰 묶음을 시작하지 않는다.

## 우선순위

1. 전날 `unverified` 항목
2. 현재 판매 중인 캐시샵 직접구매 상품
3. 대표 쿠폰/스크롤류
4. 직업 패키지 중 현재 이벤트와 직접 관련된 묶음
5. 한 패키지 안에서 고가 가능성이 큰 부위: 모자/얼굴장식/망토/무기/한벌옷
6. 부츠/슈즈처럼 보통 저가인 부위
7. 보너스 구성품, 이펙트, 케이프 등 포함 여부가 애매한 구성품

## 표준 검색 절차

1. 메이플 옥션 구매 탭을 연다.
2. 검색어 지우기를 누른다.
3. 패키지 공통 접두어를 입력한다. 예: `데몬 슬레이어`, `레지스탕스 제논`, `기사단장 오즈`.
4. 자동완성 후보 목록을 읽는다.
5. 데이터의 구성품명과 후보명을 정규화해 매칭한다.
   - 공백 제거 기준: `슈트(여)`와 `슈트 (여)`는 같은 항목으로 본다.
6. 후보가 있으면 후보를 클릭한다.
7. 선택 칩 또는 선택 상태가 실제 후보명인지 확인한다.
8. `필터 검색`을 누른다.
9. `필터 검색 결과 N건`을 기록한다.
10. 첫 결과의 가격을 기록한다.
11. 다음 항목 검색 전 다시 검색어를 지운다.

## 결과 기록 규칙

### 가격 확인 성공

`prices`에 넣는다.

```json
{
  "itemName": "데이터 기준 이름",
  "query": "경매장 후보명",
  "aliases": ["경매장 후보명이 데이터명과 다를 때만"],
  "listingLowestMeso": 123000000,
  "listingLowestText": "1억 2300만",
  "status": "ok",
  "filter": "캐시",
  "collectedAt": "2026-07-09T23:45:00+09:00"
}
```

수동 입력 가격이면 `status`와 `source`를 `manual`로 둔다.

```json
{
  "itemName": "위습의 원더베리",
  "query": "위습의 원더베리",
  "listingLowestMeso": 200000000,
  "listingLowestText": "2억",
  "status": "manual",
  "source": "manual",
  "filter": "캐시",
  "collectedAt": "2026-07-09T22:35:00+09:00"
}
```

### 후보는 있지만 매물 없음

`skipped`에 `no_listing`으로 넣는다.

```json
{
  "itemName": "데몬 슬레이어 슈트(남)",
  "query": "데몬 슬레이어 슈트 (남)",
  "status": "no_listing",
  "reason": "후보 선택 후 필터 검색 결과 0건",
  "filter": "캐시"
}
```

### 후보 없음

`skipped`에 `no_candidate`로 넣는다.

```json
{
  "itemName": "레지스탕스 메카닉 무기",
  "status": "no_candidate",
  "reason": "경매장 후보에는 레지스탕스 메카닉 건만 노출됨",
  "filter": "캐시"
}
```

### 검색 제한 또는 시간 부족

`skipped`에 `unverified`로 넣는다.

```json
{
  "itemName": "기사단장 오즈 스태프",
  "status": "unverified",
  "reason": "검색 제한 도달로 최종 가격 미확인",
  "filter": "캐시"
}
```

## 데이터 반영 위치

- 경매장 가격: `maple-cash-value/data/auction-prices.json`
- 캐시 가격/항목 구성: `maple-cash-value/data/items.json`

`auction-prices.json` 업데이트 시 함께 바꿀 것:

- `version`
- `generatedAt`
- `source`
- `policy.notes`
- `prices`
- `skipped`

가격이 `prices`에 들어간 항목은 같은 이름의 오래된 `skipped`를 남기지 않는 것이 좋다. 계산기는 가격 행을 우선하지만, 사람이 읽을 때 혼란이 생긴다.

## 오늘까지 확인된 상태

### 반영 완료

- 기본/쿠폰류 확인분
- 데몬 슬레이어 확인분
- 데몬 어벤져 확인분
- 레지스탕스 블래스터 확인분
- 레지스탕스 배틀메이지 확인분
- 레지스탕스 와일드헌터 확인분
- 레지스탕스 제논 확인분
- 레지스탕스 메카닉 확인분
- 기사단장 미하일 확인분
- 기사단장 오즈 확인분 일부

### 수동확인 또는 재확인 필요

- 기사단장 오즈 스태프: 검색 제한으로 최종 미확인
- 데몬 슬레이어 슈트(남): 매물 0건
- 레지스탕스 블래스터 헤어밴드(남): 매물 0건
- 레지스탕스 배틀메이지 모자: 경매장 후보는 `고글`만 노출
- 레지스탕스 와일드헌터 슈트(여): 매물 0건
- 레지스탕스 메카닉 무기: 경매장 후보는 `건`만 노출
- 기사단장 오즈 로브(여): 매물 0건

## 다음 검색 순서

1. 기사단장 오즈 스태프 재확인
2. 시그너스 남은 구성품
   - 기사단장 이리나
   - 기사단장 이카르트
   - 기사단장 호크아이
   - 책사 나인하트
   - 여제 시그너스
3. 영웅 패키지
   - 아란
   - 은월
   - 루미너스
   - 에반
   - 메르세데스
   - 팬텀
4. 모험가 패키지
   - 전사 계열
   - 마법사 계열
   - 궁수 계열
   - 도적 계열
   - 해적 계열

모험가까지 하루 안에 전부 확인하기 어렵다면, 고가 가능성이 높은 모자/상의/무기부터 확인하고 부츠류는 마지막에 둔다.

## 최종 보고 형식

매일 검색 종료 후 아래 형식으로 보고한다.

```text
오늘 반영:
- 가격 확인: N개
- 매물 없음: N개
- 후보 없음: N개
- 미확인: N개

남은 우선순위:
1. ...
2. ...

주의:
- 검색 제한 도달 여부
- 후보명 불일치 항목
- 사용자의 수동확인이 필요한 항목
```

## 판단 기준

최종 결론은 모든 항목이 100% 채워졌는지보다, 계산기가 신뢰 가능한 자동값과 수동확인 목록을 분리해서 보여주는지가 중요하다. 검색 제한 때문에 누락이 생기면 억지로 추정하지 말고 `unverified`로 남긴다.
