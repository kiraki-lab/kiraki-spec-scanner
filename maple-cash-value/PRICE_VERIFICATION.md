# 가격 검증과 괴리 방지 규칙

과금계산기의 순위는 "이 상품을 팔면 메소를 얼마나 받나"에 전적으로 달려 있다.
그 판매가 추정이 틀리면 순위표 전체가 틀린다. 이 문서는 그 추정을 어떤 근거로,
어떤 조건에서 믿을지 정한다.

감사 도구는 `scripts/price_audit.py`, 결과는 `data/price-audit.json`.
임계값은 두 곳이 같이 움직여야 한다.

## 1. 왜 필요한가 — 실제로 터진 것들

| 날짜 | 품목 | 무슨 일 |
|---|---|---|
| 08-16 | 루나 크리스탈 | 시세 18.89억이 채택돼 1위. 실제 매물은 2.22억, 괴리 751%. 3개월 최고 체결가 단발이 판매가 행세를 했다 |
| 08-16 | 빅풋 슈트 | 저장 시세 1.69억이 08-04에 멈춰 있었는데, 실제로는 08-11에 5.19억 체결. 낮은 값이 채택되며 3배 후려쳐졌다 |
| 08-16 | 시세 14건 재조회 | 그중 **13건**이 저장값보다 높은 체결이 3개월 안에 실재했다. 기준이 틀린 게 아니라 값이 낡아 있었다 |
| 08-23 | 마네킹 | 매물이 1건만 남았고 그 호가가 99.99억. 시세 11억이 있어 막혔다 |
| 08-23 | 상반기 BEST 프리미엄 성형 쿠폰 | 일주일 만에 2.5배(1.73억→4.33억), 시세 없음. 그대로 1위가 됐다 |

교훈은 셋이다.

- **한 근거만으로는 못 믿는다.** 매물 최저가도, 시세도 각자의 방식으로 틀린다.
- **낡은 값은 틀린 값이다.** 특히 낮은 쪽으로 낡으면 `min()` 규칙이 그걸 집는다.
- **급변은 상승만 위험한 게 아니다.** 하락 급변도 같은 크기의 오류다.

## 2. 근거 두 축과 각각의 함정

| 근거 | 필드 | 뜻 | 함정 |
|---|---|---|---|
| 매물 최저가 | `listingLowestMeso` | 지금 경매장에 올라온 가장 싼 호가 | 아무도 안 사는 호가일 수 있다. 매물이 1~2건이면 통째로 이상치 |
| 시세 | `marketPriceMeso` | 최근 체결 기반 (7절) | 갱신이 안 되면 조용히 낡는다 |
| (구) 시세 | `marketHistoryMaxMeso` | 최근 3개월 **최고 체결가** | 최고가는 도달 불가능한 값이다. 체결 내역을 못 뜬 행만 `legacyMax` 로 남아 있다 |

두 값이 가까우면 서로를 검증해 준다. 멀어지면 둘 중 하나가 틀린 것이고,
**어느 쪽이 틀렸는지는 신선도로 가린다.**

## 3. 신뢰 등급

`scripts/price_audit.py` 가 모든 행에 매긴다.

| 등급 | 조건 | 뜻 |
|---|---|---|
| **A** | 매물·시세 둘 다 3일 이내 + 괴리 30% 이내 | 그대로 쓴다 |
| **B** | 두 근거 모두 14일 이내 유효 + 괴리 60% 이내 | 그대로 쓴다 |
| **C** | 근거가 하나뿐(교차검증 없음), 또는 괴리 60% 초과 | 쓰되 검증 큐에 올린다 |
| **D** | 두 근거 모두 14일 초과, 또는 매물 2건 이하 단독 근거 | 순위 상위권이면 표시에서 경고 |
| **F** | 근거 없음, 매물 0건 + 시세 없음, 정확일치 미포착 | 계산에서 제외 |

임계값: 신선 3일 / 낡음 14일 / 저매물 2건 / 괴리 30·60%.

**`F` 의 「계산에서 제외」는 계산기도 지켜야 한다.** 정확일치 미포착 행은 원장에
직전 확인가를 보존하지만(7절), 그 값을 계산에 쓰지는 않는다. 09-20 이전의
`app.js` 는 보존된 양수 가격을 먼저 돌려주어 상태 검사에 닿지 못했다. 지금은
`status === 'uncaptured'` 를 채택보다 먼저 본다. 미포착은 값이 **없는** 것이
아니라 **모르는** 것이고, 모르는 값으로 순위를 매기면 안 된다.

## 4. 채택 규칙

현행 `app.js` 는 두 값이 다 있으면 무조건 낮은 쪽을 쓴다. 이건 **둘 다 신선할 때만** 옳다.
낡은 값을 후보에서 먼저 뺀 뒤 낮은 쪽을 고른다.

```
후보 = []
매물가가 있고 14일 이내면      후보에 넣는다
시세가 있고 14일 이내면        후보에 넣는다

후보가 비었으면   -> 있는 값을 쓰되 등급 D
후보가 하나면     -> 그것을 쓰되 등급 C
후보가 둘이면     -> 낮은 쪽 (현행 min 유지)
```

낮은 쪽을 고르는 이유는 보수성이다. 파는 사람은 최저 호가보다 비싸게 못 팔고,
아무도 안 산 호가로도 못 판다.

### 계산기와 감사가 반드시 같아야 하는 것

2026-09-20 코덱스 판정 네 번(7·7·3·2건)에서 나온 지적의 대부분이 **`app.js` 와
`price_audit.py` 가 조용히 갈라진 자리**였다. 각각은 그럴듯하게 생겨서 읽어서는
못 잡는다. 아래가 지금까지 실제로 갈라졌던 지점이다.

| 항목 | 규칙 |
|---|---|
| 후보가 0개일 때 | **시세를 먼저** 쓰고, 없으면 매물 (`market or listing`) |
| 신선도 | 시간 단위로 잰다. 날짜 차이로 재면 14.5일이 갈린다 |
| 날짜만 있는 값 | **UTC 자정**으로 읽는다 (`new Date('2026-09-06')` 규칙) |
| 비교 전 반올림 | 100만 단위로 **먼저 반올림한 뒤** 비교한다 |
| 반올림 방향 | 정확히 절반이면 **올린다**. 파이썬 `round` 는 내리므로 `floor(x+0.5)` |
| `marketPriceBasis` 없음 | 시세 값이 있으면 **legacyMax 로 본다**. 교차검증으로 인정하지 않는다 |
| `status: uncaptured` | 값을 채택하지 않는다. 보존은 원장에만 |
| 시세 탭 체결 없음 | 신선한 호가가 있어도 값을 채택하지 않는다 |
| 판매 상태 | `saleStatus` ↔ `sale_status` 여섯 값이 같아야 한다(10절 컬렉션 모델) |
| 판매 창 시각 | ISO 형식만 받는다. 달력에 없는 날·24시·1970 년 전·슬래시 날짜는 **기간 미확인** |
| 판매 창 모양 | 날짜 없는 창은 `type: "always"` 일 때만 열린 창. 그 밖에는 시작·끝 둘 다, 시작 ≤ 끝. 컬렉션 회차는 늘 둘 다 |
| `availability` 없음 | 값이 없을 때(`null`)만 상시판매. `false`·`0`·`""`·`[]` 처럼 값은 있는데 창이 아니면 **기간 미확인** |
| 괴리율 | 분모는 **매물가**. `|매물 − 시세| / 매물` (1절 751% 사례와 같은 식) |
| `seedMesoPrice` | 가격 칸에는 보여 주되 **순위에는 올리지 않는다** |
| 구성품의 `seedMesoPrice` | 패키지 합산에서도 뺀다. 단독만 막으면 패키지 문으로 들어온다 |
| 판매 기간 | 그릴 때마다 현재 시각으로 다시 판정한다. 한 번 굳히면 안 된다 |

대조 스크립트는 **파일을 쓰지 않는다.** 감사에 표준 입력으로 넘기고 표준 출력으로 받는다
(`price_audit.py --prices - --out -`). 검증자의 읽기 전용 샌드박스에서도 그대로 돌아야
대조 결과를 남이 재현할 수 있다 — 09-23 v1 판정에서 코덱스가 임시 파일 때문에 실행을 못 했다.

대조는 단독 행만이 아니라 **패키지 합산까지** 본다. 구성품을 더하는 경로가 검사
밖이면 그 문으로 들어온다(실제로 그랬다). 지금 패키지 106개를 함께 대조한다.

**대조 스크립트는 규칙을 베껴 쓰지 않는다.** `hasNoPriceEvidence` 같은 판정
함수를 `app.js` 에서 통째로 떼어 와 호출한다. 베껴 쓰면 앱을 고쳐도 검사가
안 걸린다 — 실제로 한 번 그렇게 놓쳤다.

**손으로 지키지 않는다.** `node scripts/crosscheck_adoption.js` 가 원장 전 행과
`scripts/adoption-cases.json` 의 합성 사례를 함께 돌려 불일치를 센다. 규칙을
고치면 이것부터 돌린다. 새 갈라짐을 찾으면 사례로 추가한다.

## 5. 이상치 방어

**저매물 단독 근거** — 쓸 수 있는 시세가 없는데 매물이 2건 이하이면 등급 D이고,
**구성품이 없는 단독 상품은 순위에서 뺀다.** 순위 자리에 `검증 필요` 를 표시한다.
패키지는 여러 구성품으로 평균되므로 `저매물 N개` 뱃지만 달고 순위는 유지한다.

마네킹이 이 규칙이 필요한 이유를 두 번 보여줬다. 08-23 에는 매물 1건 99.99억을
시세 11억이 막았는데, 08-27 이 되자 그 시세가 15일째라 신선도 규칙에 걸려 후보에서
빠졌고 99.99억이 그대로 채택돼 **187원으로 1위**가 됐다. 상한 역할을 하던 값이
늙어 사라지면 막을 것이 없다. 그래서 경고가 아니라 제외로 바꿨다.

**그런데 코드가 이 문장보다 좁았다.** 2026-09-20 코덱스 판정에서 드러났다.
`app.js` 는 "쓸 수 있는 후보가 정확히 1개"일 때만 저매물로 봤는데, 매물마저
14일을 넘겨 후보가 **0개**가 되면 그 조건을 빠져나가 순위에 올라왔다. 근거가 더
약해졌는데 방어가 풀리는 셈이다. 판정 대상은 후보 개수가 아니라 **교차검증으로
인정할 수 있는 시세가 있는가**로 바꿨다. `legacyMax` 는 방패로 치지 않는다(9절).
`price_audit.py` 도 같은 식으로 맞췄고, 감사의 근사 순위에서도 단독 저매물 상품을
뺀다.

**근거 없음** — 매물도 시세도 없는 행은 **순위를 매기지 않는다.** 순위 자리에
`가격 없음` 을 표시한다.

계산기의 효율식은 마일리지 5% 적립을 수익에 더한다. 그래서 메소 값이 0 이어도
효율이 무한이 아니라 **유한한 숫자로 나왔다.** 2026-09-20 에 새로 넣은 캐치! 티니핑
굿즈 컬렉션이 조회 전인데 188,000원으로 순위에 올라왔다. 맨 아래라 눈에 띄지
않았을 뿐, 그 숫자는 "가치가 낮다"가 아니라 "아직 모른다"는 뜻이다.

`price_audit.py` 의 `approx_ranking` 은 처음부터 값이 0 인 행을 건너뛰고 있었다.
계산기만 빼지 않아 감사와 화면이 다른 순위를 말하고 있었다. 적용 후 3건이 빠졌다
(캐치! 티니핑 굿즈 컬렉션 2종, 성별 변경 쿠폰 — 09-14 조회에서 매물 없음).

**초기값만 있는 행** — `seedMesoPrice` 는 손으로 적어 둔 추정치다. 경매장에서
확인한 값이 아니므로 **순위를 매기지 않고** `초기값` 으로 표시한다. 가격 칸에는
그대로 보여 준다(중고 시세를 가늠하러 오는 경우가 있다).

`app.js` 는 근거가 없을 때 이 값을 채택해 **유한한 효율을 내고 있었다.** 지금
원장에 걸린 13개는 모두 경매장 행이 있어 실제로 쓰이지는 않았지만, 행이 사라지거나
매물 0 으로 잡히면 곧바로 추정치가 순위에 오른다. 판매 종료·저매물·가격 없음을
막아 놓고 이 문만 열어 두면 의미가 없다.

**구성품의 초기값도 같다.** 단독 상품만 막았더니 패키지 합산이 남았다. 문을 하나
닫으면 옆 문이 보인다 — `totalPriceFor` 도 초기값 구성품을 0 으로 더한다.
`price_audit.approx_ranking` 이 구성품의 `calcAdoptedMeso` 를 더하는 것과 같다.

**급변** — 직전 확인가 대비 2배 이상이거나 **0.5배 이하**면 매물 수와 무관하게 플래그한다.
08-23까지의 규칙은 `매물 10건 이하 + 2배 이상`이었고, 그 그물을 상반기 BEST 성형 쿠폰
(매물 20건, 2.5배)이 빠져나가 1위가 됐다. 매물 수 조건은 뺐고 하락도 대칭으로 본다.

**1.5배 이상 + 시세 없음** — 교차검증할 것이 없으면 배수가 낮아도 플래그한다.

이 세 갈래를 `price_audit.detect_spike` 가 구현한다. **09-20 이전에는 이 함수가
정의만 돼 있고 아무도 부르지 않았다.** 플래그는 회차 러너가 남긴
`lastSearchRun.pendingHistoryItems` 만 읽었으므로, 러너가 놓친 급변은 아무도
잡지 못했다(보스 성형 쿠폰 2.19배가 실제로 빠져 있었다). 지금은 원장 값으로
직접 판정한 것과 회차 플래그를 합치고, 결과를 `price-audit.json` 의 `spikes` 에
남긴다.

## 6. 검증 예산 배분

하루 100회 × 계정 수가 전부다. 564행을 매일 다 볼 수 없으므로 순서를 정한다.

### 대역별 유지 목표 (2026-09-20)

전 품목 14일 한 기준으로 돌리던 것을 **순위표 영향도**로 바꿨다. 행이 떠받치는
상품 중 가장 높은 순위로 대역을 정하고, 대역마다 목표 신선도와 확인할 축이 다르다.

| 대역 | 목표 신선도 | 확인 축 |
|---|---|---|
| 1~20위 | 3일 | 매물 + 시세 |
| 21~40위 | 7일 | 매물 + 시세 |
| 41~80위 | 21일 | 매물만 |
| 81위 이하 | 회차당 표본 몇 건 | 매물만 |
| 어떤 판매 중 상품도 안 떠받침 | 요청 시에만 | — |

기한이 안 된 축은 큐에 넣지 않는다. 한 품목의 두 축은 따로 기한을 보므로,
매물만 낡았으면 매물만 다시 본다.

81위 이하를 **완전히** 버리지 않는 이유가 있다. 영영 안 보면 값이 올라도 순위로
올라올 수가 없어서 낮은 순위가 스스로를 가둔다. 그래서 회차마다 가장 오래된
몇 건을 표본으로 섞는다(`build_run_plan.py --sample`, 기본 5).

### 그 안에서의 순서

1. **거래 확인** — 계산기에 아직 없는 품목의 거래 가능 여부(`data/check-queue.json`)
2. **신규·미조회** — 판매 중인 상품을 떠받치는데 값이 아예 없는 행.
   값이 없으면 순위가 안 잡히고 순위가 없으면 우선순위도 안 잡히므로 점수와
   무관하게 맨 앞에 둔다
3. **상위 20위를 떠받치는 등급 C 이하** — 순위표가 실제로 서 있는 지반
4. **급변 플래그** — 상승·하락 모두
5. 대역 순서대로, 기한을 많이 넘긴 것부터

`price_audit.py` 의 `verificationQueue` 가 이 순서로 정렬된 목록을 주고,
`build_run_plan.py` 가 그날 예산만큼 잘라 `data/run-plan-<날짜>.json` 으로 남긴다.
점수는 순위 가중(상위 20위는 압도적) + 등급 + 사용처 수 + 기한 초과 + 플래그 가산.

**두 축은 같은 품목에 겹쳐 찍는다.** 등급 A 는 매물·시세가 둘 다 3일 이내여야 나온다.
08-27 회차는 매물 44 / 시세 30 을 서로 다른 품목에 나눠 써서 A 가 0 이었다.
08-30 회차에서 상위권 구성품 37종에 두 축을 함께 찍자 A 가 처음으로 14행 나왔다.

권장 편성: **비패키지 일일 우선 + (상위권 구성품 N종 × 2축)**. 남는 회차만 단축 갱신에 쓴다.

### 회차는 자정을 넘겨 이어 돌린다

검색 횟수는 자정에 초기화된다. 남은 몫을 버리지 않도록 **한도에 걸리면 멈추지 말고
리셋을 기다렸다가 이어서 돈다.** 러너는 검색을 눌렀는데 카운터가 안 오르고 100 이면
한도 소진으로 보고, 30초마다 확인하다가 카운터가 되감기면 그 품목부터 재개한다.

한 회차가 두 날짜에 걸치므로 `searchIndex` 가 중간에 1 로 되감긴다. 병합할 때
`segments` 에 날짜별 회수를 남기고 `crossedMidnight` 를 표시한다.

## 7. 회차 진행 순서

1. `python scripts/price_audit.py` 로 큐를 뽑는다
2. 큐 상위 + 비패키지 일일 우선 품목으로 그날 100회를 채운다
3. 수집 결과를 병합한다. 이때
   - 매물 0건 → `no_listing`, 직전 확인가는 `lastKnownListing*` 로 보존
   - 이름 미포착 → `uncaptured`, **기존 가격을 덮어쓰지 않는다**
   - 급변 → `pendingHistoryItems` 에 기록
4. 병합 후 `price_audit.py` 를 다시 돌려 등급 분포가 나아졌는지 본다
5. 계산기를 띄워 상위 10위가 등급 C 이하 근거 위에 서 있지 않은지 확인한다

## 8. 수집 자체의 함정 (겪은 것)

- **결과를 브라우저 메모리에만 두지 않는다.** 탭이 닫히면 100회가 통째로 날아간다(08-19 실제 발생).
  크롬은 자동 다운로드를 두 번째부터 막으므로, 페이지에 찍어 읽어내는 경로를 쓴다.
- **백그라운드 탭은 타이머가 초당 1회로 조인다.** `setTimeout` 대신 MessageChannel 기반 대기를 쓴다.
- **장비류와 소비류는 결과 행 구조가 다르다.** 인덱스 고정 파싱은 장비를 통째로 놓친다.
- **페이지 넘김은 검색 횟수를 소모하지 않는다.** 짧은 이름은 12페이지까지 넘겨 찾는다.
- **정지 플래그를 되돌려 재실행하면 이전 루프가 되살아난다.** 세대 토큰으로 무효화한다.

## 9. 시세 기준 — 최근 체결 기반으로 확정

`최근 3개월 최고 체결가` 는 버렸다. 파는 사람이 도달할 수 없는 값이라 판매가 추정에 맞지 않는다.

**채택 규칙: 최근 체결가와 최근 3건 중앙값 중 높은 쪽.** (`scripts/apply_market_basis.py`)

두 개를 섞는 이유가 있다.

- 최근 체결가 하나만 쓰면 단발 저가에 끌려간다.
- 최근 3건 중앙값만 쓰면 오르는 품목에서 뒤처진다. 빅풋 슈트는 8월에 3배 올랐는데
  중앙값은 3.67억에 머물렀고 실제 최근 체결과 매물은 5.19/5.20억이었다.
- 높은 쪽을 쓰면 상승은 따라가고 단발 저가는 막힌다. 고가 이상치는 4절의
  `min(시세, 매물)` 이 막는다.

검증: 체결 내역을 뜬 14개 품목에서 이 기준으로 계산한 값과 당시 매물 최저가의
차이는 중앙값 약 1% 였다. 기존 최고가 기준은 같은 품목에서 20~70% 벌어져 있었다.

### 이행 상태

전면 교체가 아니라 근거가 생기는 대로 옮긴다. 2026-09-20 기준 564행:

| 상태 | 행 수 | 뜻 |
|---|---|---|
| `recentSale` | 83 | 체결 내역을 떠서 새 기준으로 계산 |
| `legacyMax` | 32 | 옛 최고가만 남아 있음 |
| 없음 | 449 | 시세 축 자체가 없음 |

(2026-08-23 첫 집계는 14 / 50 / 498 이었다. 회차마다 바뀌는 숫자이므로
`python scripts/price_audit.py` 를 돌린 날짜와 함께 갱신한다.)

`legacyMax` 행의 취급이 계산기와 감사에서 다르다. **의도한 것이다.**

- **계산기**: 후보로 계속 쓴다. 과대평가지만 상한 역할을 한다. 마네킹의 매물 1건
  99.99억 호가를 막아 준 게 이 값이다.
- **감사**: 교차검증으로 인정하지 않는다. 등급 C 로 내리고 검증 큐 위로 올린다.

**갈라도 되는 것은 등급뿐이다.** 2026-09-20 코덱스 판정에서, 이 차이가 등급을 넘어
**저매물 판정과 순위 포함 여부까지** 번지고 있던 것이 드러났다. 매물 2억·legacyMax
1억·매물 1건이면 계산기는 1억을 채택하므로 호가 하나가 값을 정하는 상황이 아닌데,
감사는 legacyMax 를 뺀 채 2억을 보고 저매물로 판정해 순위에서 뺐다.

그래서 감사가 값을 두 개 들고 있게 했다.

| 필드 | 무엇 | 쓰는 곳 |
|---|---|---|
| `adoptedMeso` | 감사 기준(legacyMax 제외) | 등급 판정 |
| `calcAdoptedMeso` | **계산기가 실제로 쓰는 값** | 저매물 판정, 근사 순위, 신규 판정 |

화면과 같아야 하는 판단은 전부 `calcAdoptedMeso` 를 쓴다.

시세 축이 없는 449행이 지금 제일 큰 구멍이다. 6절의 예산 배분에서 시세 검증
비중을 당분간 높게 잡는 이유다.

## 10. 살 수 없는 상품은 순위에 없다

가격이 맞아도 **지금 살 수 없는 상품이면 "사서 팔면 이득"이라는 순위 자체가 성립하지 않는다.**

2026-08-23 에 상반기 BEST 프리미엄 성형 쿠폰이 736원으로 1위였다. 이 상품은
**08-19 23:59 에 판매가 끝났다.** 공급이 끊기면 매물가는 오르는 게 정상이고
(일주일 만에 1.73억 → 4.33억), 살 수 없는 상품의 오른 매물가가 그대로 효율 1위로 나타났다.

`items.json` 에는 이미 판매 기간이 들어 있었는데 계산기가 읽지 않고 있었다.

```json
"availability": { "type": "limited",
                  "startAt": "2026-07-23T10:00:00+09:00",
                  "endAt": "2026-08-19T23:59:00+09:00" }
```

규칙:

- `availability.endAt` 이 지났거나 `startAt` 이 아직이면 **순위를 매기지 않는다**
- `rankEligible: false` 도 같게 취급한다
- 목록에서 지우지는 않는다. 순위 자리에 `판매 종료` 와 종료일을 표시해 남긴다.
  중고 시세를 보러 오는 경우가 있고, 조용히 사라지면 왜 없어졌는지 알 수 없다

적용 후 1위는 레지스탕스 블래스터 패키지(여) 1,046원. 판매 종료 4건
(상반기 BEST 헤어·성형 쿠폰, 부티크 기프트, 부티크 기프트 10개)이 순위에서 빠졌다.

### 컬렉션 모델 — 다음 회차가 열려도 이어지게 (2026-09-23)

판매 기간을 상품마다 적어 두면 다음 회차가 열릴 때 100개 넘게 손으로 고쳐야 하고,
하나라도 빠뜨리면 이번처럼 판매 종료 상품이 순위에 남는다. 그래서 **판매 기간을
상품 밖으로 뺐다.**

- `data/collections.json` — 컬렉션마다 판매 회차(`runs`) 목록. 회차마다 공지 번호가 붙는다
- `items.json` 의 상품은 `"collection": "illust-adventurer"` 처럼 id 만 가진다
- 일회성 판매(티니핑·스페셜 루나 크리스탈 등)는 지금처럼 상품의 `availability` 를 쓴다

| 컬렉션 id | 이름 | 상품 |
|---|---|---|
| `boss` | 메이플스토리 보스 컬렉션 | 24 (패키지 22 + 보스 헤어·성형 쿠폰) |
| `illust-adventurer` | 전 직업 일러스트 컬렉션 : 모험가 | 24 |
| `illust-cygnus-hero` | 〃 시그너스 & 영웅 | 23 |
| `illust-demon-resistance` | 〃 데몬 & 레지스탕스 | 14 |
| `illust-nova-leaf` | 〃 노바 & 레프 | 9 |
| `illust-kinesis-zero-anima` | 〃 키네시스 & 제로 & 아니마 | 10 |
| `illust-hair` | 전 직업 일러스트 컬렉션 헤어 쿠폰 | 1 |

**판매 상태는 여섯 가지다.** 계산기 `saleStatus` 와 감사 `sale_status` 가 같은 값을 낸다.

| 상태 | 뜻 | 순위 |
|---|---|---|
| `on` | 회차 기간 안 | 올린다 |
| `always` | 판매 기간 정보가 없음 = 상시판매 | 올린다 |
| `upcoming` | 다음 회차가 공지됐고 시작 전 | 안 올린다 · `판매 예정` |
| `resting` | 주기 컬렉션의 휴지기 | 안 올린다 · `휴지기` (보기에서 켜면 참고 순위) |
| `ended` | 일회성 판매 끝, 또는 `rankEligible: false` | 안 올린다 · `판매 종료` |
| `unknown` | 없는 컬렉션 id, 또는 판매 창을 읽을 수 없음 | 안 올린다 · `기간 미확인` |

`unknown` 이 중요하다. 컬렉션 id 오타나 날짜 형식 실수를 **열린 창(상시판매)으로
읽으면 영원히 판매 중이 된다.** 이번 사고가 바로 「비어 있으면 상시판매」였다.
못 읽는 것은 순위에서 빼고 표시한다.

**판매 창 모양도 엄격하다.** 상품의 `availability` 에서 날짜가 하나도 없는 창은
`"type": "always"` 라고 적었을 때만 상시판매로 읽는다(로얄 스타일·프리미엄 쿠폰 등 12개가
이 모양이다). 빈 객체 `{}`, 끝만 있는 창, 시작만 있는 창, 시작이 끝보다 뒤인 창,
상시라면서 날짜가 있는 창은 전부 `unknown` 이다. 컬렉션 회차는 늘 시작·끝이 둘 다 있어야
한다. 09-23 코덱스 판정(`collections-0923` v1)에서 빈 창이 열린 창으로 새는 것이 잡혔다.

**판매 창 시각은 ISO 형식만 받는다.** 브라우저(V8)는 `2026/06/18`, `2026-02-30`(3월 2일로
넘김), `T24:00` 을 읽지만 파이썬은 거부해 두 구현이 갈라진다. 날짜만 있으면 UTC 자정,
오프셋 없는 시각은 로컬(KST)이다. `collections.json` 은 전부 `+09:00` 을 붙여 적는다.

### 휴지기 동안 하는 일

1. **화면** — `휴지기 포함` 을 켜면 휴지기 상품까지 넣은 참고 순위를 본다. 순위 칸에
   `휴지기` 꼬리표가 붙는다. 기본은 꺼져 있고, 요약의 「최고 효율」은 늘 지금 살 수
   있는 것만 본다. 위쪽 띠에 휴지기 상품 수를 알린다
2. **가격 유지** — 휴지기 참고 순위 40위 안을 떠받치는 행은 `휴지기` 대역(30일·매물만)으로
   큐 맨 뒤에 붙는다. 지금 살 수 있는 것을 다 본 뒤 남는 예산으로만 돈다. 다음 회차가
   열리는 날 구성품 수백 개가 한꺼번에 몇 달 묵은 값이 되지 않게 하려는 것이다
3. **신호** — `content_signals.py` 가 컬렉션 회차를 읽는다. 회차 끝 14일 전부터
   「판매 종료 임박」, 새 회차 시작 7일 안이면 「신규 판매」다. 「급등·급락」은 체결 기준
   50% 이상 움직였고, 체결이 4건 이상이며, 첫·끝 체결 사이가 10일 이상일 때만 잡는다
   (`MOVE_PCT` · `MOVE_MIN_SAMPLES` · `MOVE_MIN_SPAN_DAYS`). 10일보다 짧은 구간의 변화는 잡음으로 본다. 09-10 에 돌렸다면
   107개 종료 임박이 떴을 것이다

### 다음 회차가 공지되면

```bash
python scripts/add_collection_run.py --list
python scripts/add_collection_run.py illust-adventurer --start 2026-12-17T10:00 --end 2027-03-17T23:59 --notice <공지번호>
python scripts/add_collection_run.py illust-adventurer ... --apply
python scripts/price_audit.py && node scripts/crosscheck_adoption.js
```

미리보기가 기본이고 `--apply` 를 붙여야 바뀐다. 공지 번호 없이는 회차를 만들지 않고,
기존 회차와 겹치면 거부한다. 일러스트 컬렉션은 그룹별 공지가 다섯 개라 다섯 번 돌린다.
새 직업 패키지(예: 레테)가 생기면 `items.json` 에 넣고 `collection` 만 달면 된다.

09-23 에 모험가 컬렉션에 시험 회차를 붙여 보니 명령 한 줄로 모험가 패키지 24개가
순위에 돌아왔다(15 → 39위). 확인 뒤 되돌렸다.
